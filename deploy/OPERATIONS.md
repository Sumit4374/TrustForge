# Deployment and recovery reference

These are configuration templates, not a verified production deployment. The final release report distinguishes local syntax/container/restore checks from actual TLS, ACL, DNS, managed services, backups and remote CI evidence.

Use exactly one worker-owning server. The fixed server container name makes Compose reject scaling this deployment above one replica; cross-host/multi-deployment ownership remains an operator requirement, not a distributed lock. `compose.production.yaml` publishes no backend or datastore ports; attach a real TLS ingress to its private network and route to client8080. Supply server-only credentials from a deployment secret manager at runtime, never Docker build arguments, source control or frontend environment. Docker roots are read-only, capabilities dropped, temporary directories bounded and resources limited. Both application containers run as dedicated nonroot users. Validate actual certificates and HTTPS/HSTS at the ingress; `ingress.conf` uses deliberate .test/certificate placeholders. Configure trusted ingress rate limiting and preserve a reviewed forwarding policy; the current application treats proxy requests as the proxy IP rather than blindly trusting spoofable forwarding headers.

Managed PostgreSQL must require TLS with certificate/hostname verification in DB_URL, private network ACLs and a narrowly scoped application account. Use separate authenticated TLS Redis services: persisted non-evicting session/rate-limit storage and bounded evictable ordinary cache. Do not expose Mailpit in production. Verify authenticated STARTTLS SMTP, Secure/HttpOnly/SameSite cookies, same-origin CSRF, private Actuator details, readiness, and session outage503/recovery before deployment approval.

Back up PostgreSQL with `backup.sh` or a managed equivalent. Use a mode0600 credential file, encrypted private storage, checksums, retention and separately controlled access. The supplied restore script refuses existing tables and only accepts explicitly authorized disposable databases whose names begin trustforge_restore_. Rehearse restores in an isolated environment and verify Flyway version, user/project/run/result counts and authorized access. Never point a rehearsal at the live application database. Local synthetic restore evidence is not proof of your production backup policy.

Before a compatible application rollback, stop the sole worker-owning instance and take a verified backup. Preserve additive migrations and historical evidence; do not run destructive down migrations. Restore into a separate database for validation before an operator-controlled switch. Interrupted running evaluations must remain failed/inconclusive evidence, never marked successful. Test TLS, ACLs, recovery timing, dependency/image scans, isolated DAST and actual CI in the target environment before claiming production readiness.

Transient PostgreSQL failures also reconcile RUNNING jobs whose in-process worker has exited. Active workers are excluded; cancelled states are never overwritten. Queued rows survive the outage. No model decision or simulated side effect is automatically repeated. Replay explicitly creates a separate linked run after recovery.
